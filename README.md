# FilePumper

**Накачивает файл до нужного размера или прячет один файл внутри другого — с графическим интерфейсом, командной строкой и устойчивостью к обрезанию файла сервером.**

*Inflate a file to any target size, or hide a payload inside PNG / JPEG / GIF / WebP / SVG (or any other file) — GUI + CLI, written in Rust.*

## Возможности

- **Накачка до любого размера** — 6 методов: GIF-анимация, PNG-чанки, увеличение
  изображения с шумом в младших битах, SVG, ZIP/Office/PDF, случайное заполнение.
  Результат остаётся открывающимся файлом, а не «мусором с правильным размером».
- **Полезная нагрузка** — произвольный файл встраивается в PNG, JPEG, GIF, WebP, SVG
  или в хвост любого другого файла и извлекается обратно этой же программой.
- **Сжатие и пароль** — `deflate` и шифрование `Argon2id` → `ChaCha20-Poly1305`.
- **Устойчивость к обрезанию** — 1–3 копии контейнера, каждая в своём чанке или
  сегменте: если сервер или мессенджер отрежет хвост файла, уцелевшая копия всё
  равно даст исходный файл.
- **Проверка целостности** — SHA-256 блоба, CRC32 заголовка и концевого маркера;
  после записи готовый файл заново открывается декодером `image`.
- **Пакетная накачка** — сразу несколько файлов за один запуск: список в окне или
  `pump file1 file2 ... --out-dir папка` в терминале. Ошибка одного файла не мешает
  остальным, в конце — сводка «готово N из M».
- **Пакетное встраивание** — один набор файлов нагрузки в несколько носителей сразу:
  `embed carrier1.png carrier2.png --payload secret.zip --out-dir папка`.
- **Файлы «с нуля»** — `generate --size 10 --type png` создаёт файл нужного размера
  без исходника: внутри криптослучайные байты, поэтому `zip`, `gzip` и `7z` его не
  сожмут, а картинка остаётся валидной (`--type bin|png|gif|jpg|webp`, `--count N`).
  Туда же можно прицепить нагрузку — файл не вырастет ни на байт.
- **Несколько нагрузок в одном файле** — повторный `--payload` упаковывает файлы в
  ZIP-бандл внутри контейнера; `extract` распаковывает его обратно по файлам.
- **Гибкий размер** — `--size-mode exact|at-least|add` (ровно столько, не меньше или
  прибавить) и список размеров `--size 5,10,2` — по размеру на каждый файл
  (дробные размеры — через точку: `--size 1.5`).
- **Имена результатов на выбор** — размер в имени (`photo_10MB.png`) убирается
  кнопкой «Убрать размер из имени» или флагом `--names plain`, а галочка «Случайное
  имя файла» (`--names random`) даёт нейтральные имена вида `quiet-river-4821.png`.
  Работает и для пакета: имена получает каждый файл списка.
- **Папки и списки** — `--from-dir ПАПКА [--recursive] [--ext png,jpg]` и
  `--from-file список.txt`; в окне папку можно просто перетащить.
- **План и отчёт** — `--dry-run` показывает, что и куда будет записано, ничего не
  создавая; `--report отчёт.csv|.json` сохраняет результат по каждому файлу.
- **Параллельная обработка** — `--jobs N` обрабатывает до 16 файлов одновременно.
- **`verify`** — перечитывает носитель, проверяет SHA-256 и оглавление бандла.
- **Интерфейс** — drag & drop файлов и папок, список пакета с состоянием каждого файла,
  превью перед извлечением, прогресс, кнопка «Отмена», показ результата в проводнике,
  окно свободно масштабируется, настройки (метод, размер, папка, копии) сохраняются
  между запусками.
- **CLI** — `pump`, `embed`, `extract`, `inspect`, `verify`, коды выхода `0`/`1`,
  `--help`, `--version`.

## Установка

### Готовые сборки

Архивы прикладываются к [релизам](https://github.com/Xvicd/FilePumper/releases),
а также лежат в каталоге `dist/` после локальной сборки:
`FilePumper-<версия>-windows-x64.zip` и `FilePumper-<версия>-linux-x64.tar.gz`.

| Платформа | Файл | Размер | Требования |
| --- | --- | ---: | --- |
| **Windows 10/11 x64** | `FilePumper.exe` — окно приложения, консоль не открывается | 12,2 МБ | DirectX 12 или Vulkan для интерфейса; при ошибке про DLL — [Visual C++ 2015-2022 x64](https://aka.ms/vs/17/release/vc_redist.x64.exe) |
| | `FilePumper-cli.exe` — только командная строка | 2,1 МБ | — |
| **Linux x86_64** | `file-pumper` — окно приложения | 17,5 МБ | glibc ≥ 2.17, X11 или Wayland, драйвер Vulkan/Mesa |
| | `file-pumper-cli` — только командная строка | 3,2 МБ | glibc ≥ 2.17 |

На Linux CLI-версии не нужно ничего, кроме `libc` — все графические библиотеки
подгружаются динамически и нужны только окну:

```bash
tar -xzf FilePumper-0.5.0-linux-x64.tar.gz
chmod +x linux/file-pumper linux/file-pumper-cli
./linux/file-pumper-cli --help
```

Почему бинарников два: у графической сборки на Windows оконная подсистема
(`Subsystem: Windows`), поэтому двойной клик не открывает окно консоли, но и
выводить текст ей некуда. Команды для терминала — в `*-cli` версии.

## Быстрый старт

1. Запустить `FilePumper.exe` (Windows) или `./file-pumper` (Linux).
2. **Накачка:** нажать «Выбрать файлы…» (можно сразу несколько) → метод → режим
   размера и целевой размер в МБ → при необходимости выбрать папку результатов →
   «Запустить». Список показывает состояние каждого файла; метод, размер, папка,
   имена результатов и число копий запоминаются между запусками.
   Кнопка «Убрать размер из имени» убирает пометку размера из имён результатов,
   галочка «Случайное имя файла» заменяет их на нейтральные случайные
   (`quiet-river-4821.png`) — и то и другое действует на весь список сразу.
3. **Спрятать файл:** выбрать один или несколько носителей и один или несколько
   файлов нагрузки (или перетащить их в окно; папку можно перетащить целиком) →
   задать копии/сжатие/пароль → «Вшить файл…». Несколько нагрузок упаковываются в
   бандл, несколько носителей получают результат каждый.
4. **Достать файл:** выбрать носитель → «Проверить и извлечь…» → посмотреть превью
   (имя, размер, число целых копий, шифрование) → ввести пароль → сохранить
   (для бандла — выбрать папку).

## Командная строка

| Команда | Назначение |
| --- | --- |
| `pump <вход>... --size <МБ[,МБ]> [--size-mode exact\|at-least\|add] [--names size\|plain\|random] [--out-dir ПАПКА] [--output ФАЙЛ] [--method ...] [--format gif\|png\|webp] [--from-dir ПАПКА [--recursive] [--ext ...]] [--from-file СПИСОК] [--skip-unsupported] [--jobs N] [--dry-run] [--verify] [--report ФАЙЛ]` | накачать один или несколько файлов до размера |
| `generate [--size <МБ[,МБ]>] [--type bin\|png\|gif\|jpg\|webp] [--name ОСНОВА] [--count N] [--payload <файл> [--payload ...]] [--copies 1..3] [--compress] [--password ПАРОЛЬ] [--names size\|plain\|random] [--out-dir ПАПКА] [--dry-run] [--verify] [--report ФАЙЛ]` | создать файл нужного размера без исходника (алиас `make`) |
| `embed <носитель>... --payload <файл> [--payload ...] [--out-dir ПАПКА] [--output ФАЙЛ] [--copies 1..3] [--compress] [--password ПАРОЛЬ] [--names random] [--dry-run] [--report ФАЙЛ]` | спрятать файл (или несколько) в одном либо нескольких носителях |
| `extract <носитель>... [--out-dir ПАПКА] [--output ФАЙЛ] [--password ПАРОЛЬ]` | извлечь спрятанный файл (бандл распаковывается в папку) |
| `inspect <носитель>... [--password ПАРОЛЬ]` | показать, что лежит внутри, включая оглавление бандла |
| `verify <носитель>... [--password ПАРОЛЬ]` | перечитать файл и проверить контрольные суммы |
| `--help`, `--version` | справка и версия |

```powershell
# накачать до 25 МБ методом png-chunks (методы: animation, png-chunks, upscale, svg, office, padding)
file-pumper-cli pump .\photo.jpg --size 25 --method png-chunks --output .\photo_big.png

# пакет: все файлы папки, фильтр по расширению, свои размеры и 4 потока
file-pumper-cli pump --from-dir .\photos --ext jpg,png --size 5,10 --jobs 4 --method png-chunks --out-dir .\big

# прибавить к каждому файлу 2 МБ и сохранить отчёт
file-pumper-cli pump .\a.bin .\b.bin --size 2 --size-mode add --method padding --report .\pump.csv

# посмотреть план, ничего не записывая
file-pumper-cli pump --from-dir .\photos --recursive --size 10 --dry-run

# имена без размера или случайные — сразу для всего пакета
file-pumper-cli pump .\photos\*.jpg --size 5 --names plain
file-pumper-cli pump --from-dir .\docs --size 1 --method padding --names random

# создать файл с нуля: 10 МБ, внутри случайные байты (архив его не сожмёт)
file-pumper-cli generate --size 10 --type bin --out-dir .\made

# валидная PNG-картинка ровно на 25 МБ, три штуки, имена photo_25MB.png, photo_25MB-2.png...
file-pumper-cli generate --size 25 --type png --name photo --count 3 --out-dir .\made

# создать файл и сразу спрятать в него нагрузку: размер останется ровно 10 МБ
file-pumper-cli generate --size 10 --type gif --payload .\secret.zip --password пароль --out-dir .\made

# спрятать архив в картинке: 2 копии, сжатие, пароль
file-pumper-cli embed .\photo.png --payload .\secret.zip --copies 2 --compress --password пароль

# несколько нагрузок в один носитель (внутри — ZIP-бандл)
file-pumper-cli embed .\photo.png --payload .\a.txt --payload .\b.pdf --out-dir .\out

# один набор нагрузки в несколько носителей
file-pumper-cli embed .\one.png .\two.png --payload .\secret.zip --out-dir .\out

# проверить целостность и извлечь обратно
file-pumper-cli verify .\out\photo_with_payload.png --password пароль
file-pumper-cli extract .\out\photo_with_payload.png --out-dir .\restored --password пароль
```

Пакетные команды обрабатывают файлы по очереди (или параллельно при `--jobs N`):
ошибка одного файла не прерывает остальные, в конце печатается строка «Готово: …»
по каждому файлу и сводка. Код выхода `1`, если хоть один файл не удался.

`--dry-run` печатает план (`вход -> выход (размер)`) и не создаёт ни файлов, ни
папок. `--report` пишет CSV (`input,output,status,bytes,message`) или JSON — формат
выбирается по расширению. `--skip-unsupported` молча пропускает файлы, которые
выбранный метод не умеет обрабатывать, и не считает их ошибкой.

Результаты получают имя `<имя>_<размер>MB.<расширение>` (например, `photo_10MB.png`)
и никогда не перезаписывают уже существующие файлы — при совпадении добавляется
суффикс `-2`, `-3`. `--out-dir` складывает всё в одну папку, `--output` задаёт точное
имя результата для одного файла.

`--names` меняет только имя, не содержимое: `size` — размер в имени (по умолчанию),
`plain` — без него (`photo.png`), `random` — нейтральное случайное имя из двух слов и
числа (`quiet-river-4821.png`). Режим действует на весь пакет и на пакетный `embed`
(там имеют смысл `size`/`plain` — имя и так без размера — и `random`). Если результат
пишется рядом с исходником, `plain` и `random` всё равно не трогают оригинал: занятое
имя получает суффикс (`photo-2.png`).

`generate` (алиас `make`) создаёт файл без исходника. Размер берётся из `--size`
(можно список `--size 5,10`), тип — из `--type`: `bin` (обычный файл), `png`, `gif`,
`jpg`, `webp`. Внутри всегда криптослучайные байты (`getrandom`), поэтому `zip`,
`gzip` и `7z` такой файл не сожмут; у картиночных типов сначала пишется маленькая
валидная картинка, а объём добирается внутри её структуры (приватные чанки PNG,
комментарий GIF), поэтому файл открывается как изображение. `--name` задаёт основу
имени, а `--count N` создаёт по N файлов на каждый размер из `--size`
(`--size 5,10 --count 2` — четыре файла). С `--payload` (можно несколько — тогда
внутри ZIP-бандл) нагрузка сразу прячется в созданный файл: контейнер встаёт в
заранее посчитанное место, так что размер остаётся ровно целевым. Тот же сценарий
есть в окне — раздел «5. Создать файл с нуля» с галочкой «Прицепить второе дно».

Старый синтаксис `pump <вход> <выход>` (и `extract <носитель> <выход>`) продолжает
работать с предупреждением: если второй путь ещё не существует, он считается выходным
файлом. Как только такой файл появился на диске, повторный запуск той же команды
трактует оба пути как входные — для повторяемых команд сразу используйте `--output`.
Старый вызов `embed <носитель> <нагрузка> [выход]` тоже поддерживается; новый способ —
через `--payload`.

`inspect` показывает тип носителя, имя нагрузки, размер, число целых копий,
сжатие/шифрование и оценку устойчивости к загрузке на сервер. Коды выхода:
`0` — успех, `1` — ошибка (текст в stderr).

Из исходников:

```powershell
cargo run --release --bin file-pumper-cli -- pump .\photo.jpg --size 25 --output .\photo_big.png
```

## Режимы накачки

| `--method` | Что делает | Результат |
| --- | --- | --- |
| `animation` (по умолчанию) | GIF с несколькими кадрами и лёгким шумом | валидная анимация; для `--format png\|webp` — статичное изображение, размер добивается чанками/комментарием |
| `png-chunks` | PNG + приватные чанки перед `IEND` | валидный PNG |
| `upscale` | увеличенное RGB-изображение со случайными младшими битами пикселей | валидный PNG |
| `svg` | SVG с встроенным Base64-изображением и невидимыми элементами | валидный SVG (Base64 пишется потоково) |
| `office` | ZIP/Office: дополнительная несжатая запись; PDF: поток-заполнитель перед `%%EOF`; остальное — как `padding` | валидный архив/PDF |
| `padding` | копия исходного файла + криптографически случайное заполнение | байт-в-байт исходник с хвостом |

Любую операцию можно прервать кнопкой «Отмена»: рабочий поток проверяет флаг
отмены и не оставляет «полуфайлов».

## Полезная нагрузка внутри файла

Куда попадают данные:

| Носитель | Расположение нагрузки | Файл остаётся валидным |
| --- | --- | --- |
| PNG | приватные чанки `ufPl` перед `IEND` (до 4 МБ, корректный CRC32, по чанку на копию) | да |
| JPEG | сегменты APP15 (`FF EF`) сразу после `SOI`, цепочка по 65 531 байт с номерами последовательности | да |
| GIF | Comment Extension (`21 FE`) перед трейлером `3B`, отдельный комментарий на копию | да |
| WebP | RIFF-чанк `UFP1` в конце файла с пересчётом RIFF-size, отдельный чанк на копию | да |
| SVG | элементы `<metadata id="ufpl">`, `ufpl2`, … с Base64 перед `</svg>` | да |
| прочие файлы | контейнер, дописанный в конец файла, с концевым маркером `LFPU` | хвост игнорируется большинством парсеров |

### Формат контейнера (версия 2)

```
"UFPL" | версия | флаги | длина имени | имя | длина блоба | исходная длина
       | SHA-256 блоба | [соль, nonce, параметры Argon2id] | CRC32 заголовка
       | блоб | "LFPU" | полная длина
```

- `флаги`: бит 0 — сжатие deflate, бит 1 — шифрование паролем, бит 2 — внутри
  ZIP-бандл из нескольких файлов. Неизвестные биты отвергаются.
- Пароль: ключ выводится через **Argon2id** (19 МиБ, 2 прохода, соль 16 байт),
  данные шифруются **ChaCha20-Poly1305**. Параметры KDF из файла проверяются по
  границам, чтобы чужой файл не мог потребовать гигабайты памяти.
- Целостность: SHA-256 блоба + CRC32 заголовка + CRC32/размер в концевом маркере.
  Версия 1 контейнера (только CRC32) по-прежнему читается.

### Несколько файлов в одном контейнере (бандл)

Если указать `--payload` несколько раз (или добавить несколько файлов нагрузки в
окне), они упаковываются в обычный ZIP без сжатия и кладутся в контейнер одним
блобом с флагом `FLAG_BUNDLE`:

```powershell
file-pumper-cli embed .\photo.png --payload .\note.txt --payload .\report.pdf --out-dir .\out
file-pumper-cli inspect .\out\photo_with_payload.png   # покажет оглавление
file-pumper-cli extract .\out\photo_with_payload.png --out-dir .\restored
```

`extract` распаковывает бандл по файлам (существующие файлы не перезаписываются),
`verify` проверяет SHA-256 контейнера и читает оглавление архива. Старые версии
FilePumper такой файл не прочитают, потому что флаг им неизвестен — это осознанно:
структура контейнера не менялась, добавлен только новый бит флагов.

### Зачем нужны копии

Поле «Копий нагрузки» (1–3) записывает контейнер несколько раз — каждый в свой
чанк, сегмент или комментарий. При извлечении ищутся все копии, берётся первая
целая, а их число показывается пользователю. Если сервер обрежет хвост файла,
уцелевшие копии всё равно дадут исходный файл — это проверяют тесты
`payload_survives_when_server_cuts_the_tail` и `png_payload_survives_partial_truncation`.

### Проверка после записи

После встраивания программа заново читает полученный файл, находит все копии,
сверяет контрольные суммы и пробует декодировать изображение (`image::open`) либо
проверить `<svg>`/размер RIFF. Так видно, что файл остался рабочим и сервер примет
его целиком, а не «битую картинку».

## Где файл переживёт загрузку

Результат накачки и генерации — не «мусор с правильным размером»: формат у файла
настоящий, и по первым байтам он определяется как `image/png`, `image/gif`,
`image/jpeg` или `image/webp`. Проверено на файлах по 0,1 МБ каждого типа: `PIL`
открывает и декодирует все четыре, строгая `Image.verify()` проходит без замечаний,
а сигнатура совпадает с расширением — никакого «.png поверх чужого файла».

| Тип | Что лежит внутри | Где лишние байты | Как видят проверки |
| --- | --- | --- | --- |
| `png` | подпись, `IHDR`, `IDAT`, приватный чанк `caBX`, `IEND` | внутри структуры; после `IEND` — 0 байт, CRC всех чанков валидны | самый безопасный вариант: строгий валидатор PNG такой файл принимает |
| `gif` | `GIF89a`, маленький кадр, блок комментария `21 FE`, трейлер `3B` последним байтом | внутри структуры | наравне с PNG — ничего лишнего за контейнером нет |
| `jpg` | `FF D8 FF E0` (JFIF), кадр, `EOI` | случайный хвост **после** `EOI` | браузеры, `libjpeg`, `PIL` и `image` хвост игнорируют; самописный валидатор «ровно 0 байт после `EOI`» — откажет |
| `webp` | `RIFF…WEBP` и чанки изображения | хвост **вне** RIFF (RIFF-size меньше фактической длины файла) | декодеры читают по RIFF-size и хвост не видят |
| `bin` | ничего — чистые случайные байты | весь файл | определяется как `application/octet-stream`; загрузчик картинок его отклонит |

Что важно при загрузке:

- **Сигнатура на месте.** Сервер увидит `image/*` и не отклонит файл по типу, а
  размеры в заголовках (`IHDR`, GIF-LSD, `SOF`, `VP8X`) настоящие — проверки «а это
  точно картинка и того ли размера» проходят.
- **Лимиты размера.** У аватарок, превью и соцсетей лимит обычно 2–20 МБ: файл на
  100 МБ завернут, даже если он безупречно валиден.
- **Пережатие убивает встроенное.** Соцсети, мессенджеры в режиме «фото» и
  CDN-ресайзеры перекодируют изображение: паддинг и второе дно при этом пропадают,
  а файл уменьшается до самой картинки 16×16. Отправляйте результат как
  файл/документ и кладите на хранилища, которые отдают байты как есть.
- **Строгие валидаторы.** У `jpg` и `webp` хвост лежит за пределами контейнера:
  загрузчик, требующий «файл заканчивается ровно на `EOI`/RIFF», может отказать.
  Нужна максимальная совместимость — берите `png` или `gif`.
- **Эвристики антивирусов** иногда срабатывают на большие блоки случайных данных:
  это уже про содержимое, а не про формат.

## Сборка из исходников

Нужен Rust 1.89 или новее (проверено на 1.99) и Cargo.

### Windows

```powershell
cargo build --release   # target\release\file-pumper.exe и file-pumper-cli.exe
cargo run --release     # сразу запустить окно (default-run)
```

### Linux

```bash
cargo build --release
./target/release/file-pumper-cli --help
```

Системные библиотеки для сборки не нужны: X11, Wayland и Vulkan подгружаются в
runtime (для работы окна нужны драйвер Vulkan/Mesa и `libxkbcommon`).

### Кросс-компиляция Windows → Linux

```powershell
rustup target add x86_64-unknown-linux-gnu
cargo install cargo-zigbuild --locked
# zig: https://ziglang.org/download/ — распаковать и добавить в PATH
cargo zigbuild --release --target x86_64-unknown-linux-gnu.2.17 --bins
# результат: target\x86_64-unknown-linux-gnu\release\
```

`.2.17` — минимальная версия glibc, с которой будет работать бинарник.

### Тесты и линтеры

```powershell
cargo test                        # 111 тестов: юнит, сквозные и на устойчивость
cargo clippy --all-targets
cargo fmt --check
bash scripts/check_linux_build.sh # проверка Linux-бинарника (в Linux или WSL)
```

Те же проверки выполняет CI (`.github/workflows/ci.yml`) на Windows и Linux.

## Ограничения

- Пережатие изображения (мессенджеры в режиме «фото», «Сохранить для веба»,
  скриншот) удаляет встроенные данные — отправляйте результат как файл/документ.
- Чистильщики метаданных (`exiftool -all=`, оптимизаторы PNG) вырезают неизвестные
  чанки и расширения.
- У обычных файлов нагрузка живёт в хвосте: если концевой маркер обрезан, поиск идёт
  по последним 64 МБ, поэтому копии больше этого окна находит только быстрый путь по
  маркеру.
- Один контейнер ограничен 512 МБ, суммарный объём копий при чтении — 1,5 ГБ;
  нагрузка читается в память целиком. Для бандла лимит считается по сумме файлов
  нагрузки (ZIP хранится без сжатия).
- `--jobs N` ускоряет пакет за счёт параллельной записи, но одновременно держит в
  памяти до N файлов; для очень больших объёмов оставляйте `--jobs 1`.
- GPU для обработки файлов не используется — всё считается на CPU; окно рисуется
  через `wgpu` с программным fallback.
