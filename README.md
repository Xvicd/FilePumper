# FilePumper

**Накачивает файл до нужного размера или прячет один файл внутри другого — с графическим интерфейсом, командной строкой и устойчивостью к обрезанию файла сервером.**

*Inflate a file to any target size, or hide a payload inside PNG / JPEG / GIF / WebP / SVG (or any other file) — GUI + CLI, written in Rust.*

## Возможности

- **Накачка до любого размера** — 6 методов: GIF-анимация, PNG-чанки, увеличение
  изображения с шумом в младших битах, SVG, ZIP/Office/PDF, случайное заполнение.
  Результат остаётся открывающимся файлом, а не «мусором с правильным размером».
- **Полезная нагрузка** — произвольный файл встраивается в PNG, JPEG, GIF, WebP, SVG
  или в хвост любого другого файла и извлекается обратно этой же программой.
- **Сжатие и пароль** — `deflate` и шифрование `Argon2id` → `ChaCha20-Poly1305`.
- **Устойчивость к обрезанию** — 1–3 копии контейнера, каждая в своём чанке или
  сегменте: если сервер или мессенджер отрежет хвост файла, уцелевшая копия всё
  равно даст исходный файл.
- **Проверка целостности** — SHA-256 блоба, CRC32 заголовка и концевого маркера;
  после записи готовый файл заново открывается декодером `image`.
- **Пакетная накачка** — сразу несколько файлов за один запуск: список в окне или
  `pump file1 file2 ... --out-dir папка` в терминале. Ошибка одного файла не мешает
  остальным, в конце — сводка «готово N из M».
- **Интерфейс** — drag & drop файлов, список пакета с состоянием каждого файла,
  превью перед извлечением, прогресс, кнопка «Отмена», показ результата в проводнике,
  окно свободно масштабируется.
- **CLI** — `pump`, `embed`, `extract`, `inspect`, коды выхода `0`/`1`, `--help`, `--version`.

## Установка

### Готовые сборки

Архивы прикладываются к [релизам](https://github.com/Xvicd/FilePumper/releases),
а также лежат в каталоге `dist/` после локальной сборки:
`FilePumper-<версия>-windows-x64.zip` и `FilePumper-<версия>-linux-x64.tar.gz`.

| Платформа | Файл | Размер | Требования |
| --- | --- | ---: | --- |
| **Windows 10/11 x64** | `FilePumper.exe` — окно приложения, консоль не открывается | 11,4 МБ | DirectX 12 или Vulkan для интерфейса; при ошибке про DLL — [Visual C++ 2015-2022 x64](https://aka.ms/vs/17/release/vc_redist.x64.exe) |
| | `FilePumper-cli.exe` — только командная строка | 1,7 МБ | — |
| **Linux x86_64** | `file-pumper` — окно приложения | 16,7 МБ | glibc ≥ 2.17, X11 или Wayland, драйвер Vulkan/Mesa |
| | `file-pumper-cli` — только командная строка | 2,9 МБ | glibc ≥ 2.17 |

На Linux CLI-версии не нужно ничего, кроме `libc` — все графические библиотеки
подгружаются динамически и нужны только окну:

```bash
tar -xzf FilePumper-0.3.0-linux-x64.tar.gz
chmod +x linux/file-pumper linux/file-pumper-cli
./linux/file-pumper-cli --help
```

Почему бинарников два: у графической сборки на Windows оконная подсистема
(`Subsystem: Windows`), поэтому двойной клик не открывает окно консоли, но и
выводить текст ей некуда. Команды для терминала — в `*-cli` версии.

## Быстрый старт

1. Запустить `FilePumper.exe` (Windows) или `./file-pumper` (Linux).
2. **Накачка:** нажать «Выбрать файлы…» (можно сразу несколько) → метод → целевой
   размер в МБ → при необходимости выбрать папку результатов → «Запустить».
   Список показывает состояние каждого файла, обработка идёт по очереди.
3. **Спрятать файл:** выбрать носитель и нагрузку (или перетащить оба файла в окно)
   → задать копии/сжатие/пароль → «Вшить файл…».
4. **Достать файл:** выбрать носитель → «Проверить и извлечь…» → посмотреть превью
   (имя, размер, число целых копий, шифрование) → ввести пароль → сохранить.

## Командная строка

| Команда | Назначение |
| --- | --- |
| `pump <вход>... --size <МБ> [--out-dir ПАПКА] [--output ФАЙЛ] [--method ...] [--format gif\|png\|webp]` | накачать один или несколько файлов до размера |
| `embed <носитель> <нагрузка> [выход] [--copies 1..3] [--compress] [--password ПАРОЛЬ]` | спрятать файл в носителе |
| `extract <носитель>... [--out-dir ПАПКА] [--output ФАЙЛ] [--password ПАРОЛЬ]` | извлечь спрятанный файл из одного или нескольких носителей |
| `inspect <носитель>...` | показать, что лежит внутри |
| `--help`, `--version` | справка и версия |

```powershell
# накачать до 25 МБ методом png-chunks (методы: animation, png-chunks, upscale, svg, office, padding)
file-pumper-cli pump .\photo.jpg --size 25 --method png-chunks --output .\photo_big.png

# пакет: все JPEG из папки, результаты — в отдельный каталог
$files = Get-ChildItem .\photos\*.jpg | ForEach-Object FullName
file-pumper-cli pump @files --size 10 --method png-chunks --out-dir .\big

# спрятать архив в картинке: 2 копии, сжатие, пароль
file-pumper-cli embed .\photo.png .\secret.zip .\photo_secret.png --copies 2 --compress --password пароль

# проверить содержимое и извлечь обратно
file-pumper-cli inspect .\photo_secret.png .\photo_secret2.png
file-pumper-cli extract .\photo_secret.png .\photo_secret2.png --out-dir .\restored --password пароль
```

Пакетные команды обрабатывают файлы по очереди: ошибка одного файла не прерывает
остальные, в конце печатается строка «Готово: …» по каждому файлу и сводка.
Код выхода `1`, если хоть один файл не удался.

Результаты получают имя `<имя>_<размер>MB.<расширение>` (например, `photo_10MB.png`)
и никогда не перезаписывают уже существующие файлы — при совпадении добавляется
суффикс `-2`, `-3`. `--out-dir` складывает всё в одну папку, `--output` задаёт точное
имя результата для одного файла.

Старый синтаксис `pump <вход> <выход>` (и `extract <носитель> <выход>`) продолжает
работать с предупреждением: если второй путь ещё не существует, он считается выходным
файлом. Как только такой файл появился на диске, повторный запуск той же команды
трактует оба пути как входные — для повторяемых команд сразу используйте `--output`.

`inspect` показывает тип носителя, имя нагрузки, размер, число целых копий,
сжатие/шифрование и оценку устойчивости к загрузке на сервер. Коды выхода:
`0` — успех, `1` — ошибка (текст в stderr).

Из исходников:

```powershell
cargo run --release --bin file-pumper-cli -- pump .\photo.jpg --size 25 --output .\photo_big.png
```

## Режимы накачки

| `--method` | Что делает | Результат |
| --- | --- | --- |
| `animation` (по умолчанию) | GIF с несколькими кадрами и лёгким шумом | валидная анимация; для `--format png\|webp` — статичное изображение, размер добивается чанками/комментарием |
| `png-chunks` | PNG + приватные чанки перед `IEND` | валидный PNG |
| `upscale` | увеличенное RGB-изображение со случайными младшими битами пикселей | валидный PNG |
| `svg` | SVG с встроенным Base64-изображением и невидимыми элементами | валидный SVG (Base64 пишется потоково) |
| `office` | ZIP/Office: дополнительная несжатая запись; PDF: поток-заполнитель перед `%%EOF`; остальное — как `padding` | валидный архив/PDF |
| `padding` | копия исходного файла + криптографически случайное заполнение | байт-в-байт исходник с хвостом |

Любую операцию можно прервать кнопкой «Отмена»: рабочий поток проверяет флаг
отмены и не оставляет «полуфайлов».

## Полезная нагрузка внутри файла

Куда попадают данные:

| Носитель | Расположение нагрузки | Файл остаётся валидным |
| --- | --- | --- |
| PNG | приватные чанки `ufPl` перед `IEND` (до 4 МБ, корректный CRC32, по чанку на копию) | да |
| JPEG | сегменты APP15 (`FF EF`) сразу после `SOI`, цепочка по 65 531 байт с номерами последовательности | да |
| GIF | Comment Extension (`21 FE`) перед трейлером `3B`, отдельный комментарий на копию | да |
| WebP | RIFF-чанк `UFP1` в конце файла с пересчётом RIFF-size, отдельный чанк на копию | да |
| SVG | элементы `<metadata id="ufpl">`, `ufpl2`, … с Base64 перед `</svg>` | да |
| прочие файлы | контейнер, дописанный в конец файла, с концевым маркером `LFPU` | хвост игнорируется большинством парсеров |

### Формат контейнера (версия 2)

```
"UFPL" | версия | флаги | длина имени | имя | длина блоба | исходная длина
       | SHA-256 блоба | [соль, nonce, параметры Argon2id] | CRC32 заголовка
       | блоб | "LFPU" | полная длина
```

- `флаги`: бит 0 — сжатие deflate, бит 1 — шифрование паролем. Неизвестные биты
  отвергаются.
- Пароль: ключ выводится через **Argon2id** (19 МиБ, 2 прохода, соль 16 байт),
  данные шифруются **ChaCha20-Poly1305**. Параметры KDF из файла проверяются по
  границам, чтобы чужой файл не мог потребовать гигабайты памяти.
- Целостность: SHA-256 блоба + CRC32 заголовка + CRC32/размер в концевом маркере.
  Версия 1 контейнера (только CRC32) по-прежнему читается.

### Зачем нужны копии

Поле «Копий нагрузки» (1–3) записывает контейнер несколько раз — каждый в свой
чанк, сегмент или комментарий. При извлечении ищутся все копии, берётся первая
целая, а их число показывается пользователю. Если сервер обрежет хвост файла,
уцелевшие копии всё равно дадут исходный файл — это проверяют тесты
`payload_survives_when_server_cuts_the_tail` и `png_payload_survives_partial_truncation`.

### Проверка после записи

После встраивания программа заново читает полученный файл, находит все копии,
сверяет контрольные суммы и пробует декодировать изображение (`image::open`) либо
проверить `<svg>`/размер RIFF. Так видно, что файл остался рабочим и сервер примет
его целиком, а не «битую картинку».

## Сборка из исходников

Нужен Rust 1.89 или новее (проверено на 1.99) и Cargo.

### Windows

```powershell
cargo build --release   # target\release\file-pumper.exe и file-pumper-cli.exe
cargo run --release     # сразу запустить окно (default-run)
```

### Linux

```bash
cargo build --release
./target/release/file-pumper-cli --help
```

Системные библиотеки для сборки не нужны: X11, Wayland и Vulkan подгружаются в
runtime (для работы окна нужны драйвер Vulkan/Mesa и `libxkbcommon`).

### Кросс-компиляция Windows → Linux

```powershell
rustup target add x86_64-unknown-linux-gnu
cargo install cargo-zigbuild --locked
# zig: https://ziglang.org/download/ — распаковать и добавить в PATH
cargo zigbuild --release --target x86_64-unknown-linux-gnu.2.17 --bins
# результат: target\x86_64-unknown-linux-gnu\release\
```

`.2.17` — минимальная версия glibc, с которой будет работать бинарник.

### Тесты и линтеры

```powershell
cargo test                        # 33 теста: юнит, сквозные и на устойчивость
cargo clippy --all-targets
cargo fmt --check
bash scripts/check_linux_build.sh # проверка Linux-бинарника (в Linux или WSL)
```

Те же проверки выполняет CI (`.github/workflows/ci.yml`) на Windows и Linux.

## Ограничения

- Пережатие изображения (мессенджеры в режиме «фото», «Сохранить для веба»,
  скриншот) удаляет встроенные данные — отправляйте результат как файл/документ.
- Чистильщики метаданных (`exiftool -all=`, оптимизаторы PNG) вырезают неизвестные
  чанки и расширения.
- У обычных файлов нагрузка живёт в хвосте: если концевой маркер обрезан, поиск идёт
  по последним 64 МБ, поэтому копии больше этого окна находит только быстрый путь по
  маркеру.
- Один контейнер ограничен 512 МБ, суммарный объём копий при чтении — 1,5 ГБ;
  нагрузка читается в память целиком.
- GPU для обработки файлов не используется — всё считается на CPU; окно рисуется
  через `wgpu` с программным fallback.
